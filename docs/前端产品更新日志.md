## 2026-08-11

### 🐛 接上真后台后，App 不再自己给自己「发钱、发货、宣布到账」——一族五处

**概述**：这套 app 有两种运行档：演示档（数据都是本地编的）和真后台档，而**真后台档是默认档**（不设环境变量就是它）。本轮查出五处该由服务器说了算的事，在真后台档下仍由手机自己算、自己推进——判断依据是**手机上的时间**或一次随机数。把手机时间往前拨，App 就会宣布提现「已到账」、余额自己长、订单自己发货，钱其实一分没动。五处全部改为真后台档下不再自作主张，并补上「问服务器要状态」的回读路径。

**要点**

- 🐛 **提现到账**：单子是服务器开的（含预计到账时刻），到点后却由手机判「已到账」。这一处最伤——它同时解掉了两道资金闸：换绑收款地址、以及「同时只能有一笔提现」。改为真后台档下不自推，状态改由**向服务器逐单回读**；只关不接的话单子会永远停在「处理中」，那两道闸就永远解不开，等于把一个毛病换成另一个；
- 🐛 **挖矿收益计提**：本地按手机时间累加收益，并且不止改显示的数字——它会一路写进 USDT 余额、NEX 余额和可提现额度。旁边同一个文件里的另一个定时器早就有这道闸，唯独计提这条漏了；
- 🐛 **订单履约**：本地把订单一步步推到「已激活」，推到那一步还会**凭空生成并激活一台矿机**（实测：设备从 5 台变 6 台）。三个地方在推它——首页 6 秒轮询、订单详情页自带的 3 秒定时器、下拉刷新——闸焊在共用的那一处，三条路一起挡住；
- 🐛 **充值到账**：银行 / 链上 / 银行卡三条充值轨的到账全由本地扮演的「服务器」裁定，其中银行卡那条是当场加钱（实测：真后台档下调一次，余额 +$50）。四道闸一起焊上；
- 🐛 **充值页在真后台档下不再给出任何收款目标**（本条比上面几条都严重，也是最后才查出来的）：链上轨展示的「专属充值地址」是本地用伪随机数**算出来的**，形状像真地址但没有任何人持有它的私钥；银行轨展示的收款账号来自本地写死的账户表——两处都带一键复制。真后台还没接上时把它们摆出来，等于**引导用户把真钱打进一个虚构的收款目标**，链上那笔打出去就找不回来了。前面几条挡的是「假装钱到账了」，这条挡的是「真把钱送出去」，是同一件事的两面。现在真后台档下整页显示「充值暂时不可用」，并明确提示不要向此前保存过的地址或账号转账（三语齐）；
- 🐛 **收益里程碑发奖**：按本地累计收益判断有没有跨过档位，跨了就发 NEX 并记一条账单——而那个累计数正是上面第二条本地编出来的；
- ✏️ **组合购买**（购物车里凑多件打折那个入口）：它是全站最后一个还在「本地建单 + 本地扣余额」的购买入口，单品购买早已改走服务器下单。订单履约收归服务器后再放它过去，就成了「钱扣了、单子永远停在已支付、机器一台不来」——改为真后台档下先拒单，等它按每件一单接上服务器下单接口再放开；
- 🛡️ 新增一道**行为门**（不是查代码里有没有写某句话，而是真把这些模块装进 node 跑起来，直接看「钱有没有变、设备有没有多」）。两种档各跑一遍：真后台档必须一分不动，演示档必须照常工作——只测前者的话，把功能整个删掉也能过。实测把本轮改动撤掉，门立刻 12 项报红。

**入手不到的三处（查证后判定不改，一并记账）**：免费试用的到期推进、客服会话超时自动关闭——两者都没有对应的服务器接口（试用的接口当年就明确没搬），且都不涉及钱；单关掉本地推进反而会让试用永远停在「进行中」，把一个设备位永久占死。成就自动解锁不是独立问题，它读的就是上面第二条的收益数字，随之修好。下拉刷新推收益那半条本来就已经挡住了。

**另立案（本次未改，主人 2026-08-11 拍板「先停摆、后接线」）**

① **充值三条轨在真后台档下整体停摆，缺口按主人指示暂留**。主人 2026-08-11 交底三条：VietQR 已不再使用，改用新的第三方支付服务商；**服务商尚未选定**；**后端也还没开始接**（同事在处理，其仓库不在本账号可见范围内）。因此代码里现存的 VietQR 客户端（`payment-api.ts` 的意向单族，全站零调用点）是**待替换的死代码**，不要再往上接线；链上充值与银行卡本就一个接口都没有。当日 fetch 后核过 `origin/UniApp`，新服务商在本仓零痕迹。

　🔴 **接线时的形态已定：跳转到服务商的收银台页面**（不再由 app 自己展示收款账号/地址）。这把风险换了个位置，接线的人必须守住——**收银台地址只能由后端下发，客户端不许自己拼、不许写死兜底、不许跳一个来路不明的地址**。这与本轮修的是同一族缺陷：本轮挡的是「app 给出一个假的收款目标」，跳转形态下等价的失手是「app 把用户送到一个假的收银台」，而且后者更像真的、更难被用户识破。形态定了但代码一行没有，现在焊机器门只会得到一道扫不到靶子的空门，所以先记在这里；等第一段跳转代码落地，同一批把门补上。

　（另注：接口台账 `endpoint-citation-sentinel` 只是「注释可以提这个路径」的登记，不代表后端有该接口；PRD §9.2.8 的入金命名早已被真后端推翻——接线时以届时服务商与后端的实际契约为准，别照台账和 PRD 猜。）

② **组合购买在真后台档下拒单**——恢复它要先和后端定：是每件一单各发一次 `POST /api/orders`，还是给组合折扣一个能由服务端定价的单据类型；定价规则不该由客户端断言。

两条都是「加功能」不是「修缺陷」，故与本轮切开。

**入口**：钱包 → 提现 / 充值；商店 → 订单详情、组合购买；首页收益。
**PRD 章节**：无新增功能契约（把已定契约的权威归位），提现状态回读用 §9.11f 的按 id 读单通式；订单列表读回路（`GET /api/orders`）PRD 尚无条目，已在接口台账登记待补。

### ✏️ 退款失败不再假装没事:钱真被扣着时给交易号找客服,并发退款也不会凭空多钱

**概述**:一笔操作没成功时,系统会把钱原样退回。此前**退款本身失败**的那种情况被当成没事发生 —— 用户看到的仍是「余额没有变化」,而钱是真的扣走了。现在这种情况会明确告诉用户「这笔金额仍被占用」并给一个**交易号**,凭它找客服就能拿回。另外修掉一个更隐蔽的问题:在两个页面同时操作时,退款的算法会把**别人那一笔**也一起退给用户,账户余额会比原来还多。

**要点**

- 退款失败 → 独立提示 + 交易号(不再与「交易未保存」共用一句话);该笔的还原凭据会留档待对账;
- 退款成功照旧走原来的提示,不会动不动惊动客服;什么都没发生时也不会误报「钱卡住了」;
- 同一账号在两个页面各操作一次、各失败一次,退款后余额精确回到起点(此前会凭空多出一笔);
- 质押建仓时如果本机存不下这笔仓位,直接如实报失败并退款,不再「这一页看得见、刷新就没了」;失败原因分开说:是别处刚改过持仓,还是这台设备存不下(建议腾空间 / 关无痕);
- 试用转购买时,试用**在钱确实扣住之后**才被消耗 —— 此前扣款失败会把试用白白烧掉且无法恢复;扣款成功后若转化被拒,钱按原样退回。

**入口**:结算页(试用转购买)· 质押页「锁仓」· 复投页 —— 均为失败路径提示,正常成交无感知。

**PRD 章节**:§9.11e / §11(资金失败态口径)。
